# 7. Прогресс, сохранение и файл сейва

> Часть технического задания — оглавление в [SPEC_ru.md](../SPEC_ru.md).
> Английская версия — [07-progress-and-sync.md](07-progress-and-sync.md), обе должны оставаться синхронными.

Всё хранится в localStorage под одним версионированным ключом: `swedish-app:v1`.

```ts
interface SaveFile {
  version: 1;
  createdAt: string;
  profile: { name?: string; language: 'ru' | 'en' };   // интерфейс + переводы, одна настройка
  wallet: { xp: number; coins: number; level: number };
  streak: { current: number; longest: number; lastActiveDate: string; freezesAvailable: number };
  lessons: Record<LessonId, {
    attempts: number;
    bestScore: number;
    passed: boolean;
    lastAttemptAt: string;
    rewardedRunsToday: number;
  }>;
  items: Record<ItemId, {
    box: 0|1|2|3|4|5;
    dueAt: string;
    seen: number; correct: number; wrong: number;
    lastSeenAt: string;
  }>;
  city: {
    era: EraId;
    buildings: Record<BuildingId, { level: number; builtAt: string }>;
  };
  achievements: {
    unlocked: Record<AchievementId, { tier: number; at: string }>; // высший когда-либо достигнутый уровень
    counters: Partial<Record<AchievementCounter, number>>;         // события, которые больше нигде не записаны
    holidays: string[]; combo: number; day: { date: string; lessons: number };
  };
  settings: { theme: 'system'|'light'|'dark'; tts: { voice?: string; rate: number }; sound: boolean };
}
```

Правила:

- В `persist.ts` лежит карта `migrations` по версиям; сейв старой версии мигрируется вперёд,
  а не удаляется.
- Id, которых больше нет в контенте — уроки, вопросы (элементы SRS и `lastRunQuestionIds`),
  здания, исторические карточки, диалоги, достижения, — удаляются при каждой загрузке сейва: из
  localStorage, из импортированного файла или из облака (`src/store/pruneSave.ts`).
- Кнопки **Экспорт / Импорт** в настройках скачивают и загружают этот JSON. Это единственный
  способ бэкапа в приложении без бэкенда — обязателен в v1.
- Повреждённый сейв не должен ронять приложение: парсим через Zod, откатываемся к новому
  сейву, показываем неблокирующий тост.

## 7.1 Необязательная облачная синхронизация — Supabase

По умолчанию приложение без бэкенда: всё описанное выше работает без аккаунта и без сети.
Облачная синхронизация — необязательный слой поверх этого, включается вручную (Настройки →
«Синхронизация» → войти через Google), для тех, кто учится с нескольких устройств. Если не
входить — или выйти из аккаунта — приложение работает ровно так, как описано в §7.

**Где это настроено:**

- Проект Supabase (Auth + Postgres). Его URL и anon/publishable-ключ лежат в `.env.local`
  (не в git) как `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`, подставляются Vite на этапе
  сборки. Это не секреты: для статического сайта собранный JS-бандл и так уходит каждому
  посетителю, поэтому anon-ключ и задуман публичным — реальная граница доступа — это
  row-level security базы данных, а не секретность ключа. Автоматический деплой через CI
  (`.github/workflows/deploy.yml`) берёт те же два значения из репозиторных секретов GitHub
  Actions, так как `.env.local` в CI не попадает — если их там не задать, задеплоенная сборка
  соберётся без кнопки входа, при том что локально всё работает.
- `supabase/schema.sql` — выполняется один раз вручную в SQL-редакторе Supabase. Одна таблица,
  `saves(user_id uuid primary key references auth.users, data jsonb, updated_at timestamptz)`,
  с RLS-политиками, ограничивающими каждый select/insert/update условием
  `auth.uid() = user_id`. Ключ `service_role` в клиенте нигде не используется.
- Вход через Google через Supabase Auth, по потоку **PKCE**
  (`src/store/supabaseClient.ts`: `createClient(url, key, { auth: { flowType: 'pkce' } })`).
  Это не стилистический выбор, а необходимость: приложение использует `HashRouter` (§9), а
  Supabase по умолчанию (implicit-поток) возвращает сессию во фрагменте URL
  (`#access_token=...`), который конфликтует с тем, что роутер сам использует `#` для
  маршрутов, и токен просто не подхватывается. PKCE возвращает `?code=...` как query-параметр,
  который `HashRouter` не трогает.

**Карта кода:**

| Файл | Ответственность |
|---|---|
| `src/store/supabaseClient.ts` | Создаёт клиент из двух переменных окружения; `null`, если хоть одна не задана — тогда у форка без своего проекта Supabase фича просто отсутствует |
| `src/store/cloudSync.ts` | Вход/выход, чтение/запись сейва в облако и `mergeSaves()` (ниже) |
| `src/store/cloudSyncStatus.ts` | Небольшой, не персистентный Zustand-стор, отражающий статус сессии/синхронизации — чтобы его мог читать любой компонент, а не только тот, что запускает эффект синхронизации, через `useCloudSyncStatus()` |
| `src/store/useCloudSync.ts` | Сам эффект — монтируется один раз в `AppShell` — который и выполняет последовательность ниже |
| `SettingsPage.tsx` | Карточка «Синхронизация»: кнопка входа/выхода, статус |

**Последовательность:** при входе (в том числе «уже вошёл» при загрузке страницы) — забрать
облачную строку, смержить (`mergeSaves()`) её с текущим локальным `SaveFile`, записать
результат и в `localStorage` (через стор), и обратно в Supabase. Далее, пока пользователь
залогинен, каждое локальное изменение отправляется с задержкой в 10 секунд (достаточно, чтобы
весь прогон урока схлопнулся в один upsert).

**Схема слияния.** Простое «побеждает последняя запись» по всему файлу незаметно потеряло бы
прогресс с того устройства, которое не успело синхронизироваться последним — например, если
один урок пройден на телефоне, а другой — на ноутбуке до того, как оба синхронизировались.
Поэтому `mergeSaves()` мержит по отдельным полям:

| Поле | Правило |
|---|---|
| `lessons[id]` | База — запись с более свежим `lastAttemptAt`; `bestScore`/`attempts` — максимум из двух, `passed` — ИЛИ из двух |
| `items[id]` (SRS) | `box`/`dueAt`/`lastCorrect`/`lastSeenAt` — из записи, где ревью было более свежим; `seen`/`correct`/`wrong` — максимум из двух |
| `city.buildings[id]` | Побеждает запись с бо́льшим `level` целиком — здание, уже построенное дальше на одном устройстве, никогда не откатывается |
| `wallet.{xp,coins}` | `max` из двух — заработанная валюта только растёт; компромисс в том, что два независимых заработка на разных устройствах между синхронизациями не суммируются, берётся только больший |
| `streak` | Вся запись целиком берётся с более свежим `lastActiveDate` (это небольшая дата-машина состояний, мержить по полям небезопасно); `longest` — максимум из двух |
| `historyRead` / `dialoguesRead` | Объединение множеств |
| `dailyIncomeClaimedOn` | Более поздняя из двух дат — чтобы уже полученный за день бонус не выдался повторно |
| `achievements` | `unlocked`: побеждает более высокий уровень (при равенстве — более ранняя дата); `counters`: max по ключу; `holidays`: объединение; `day`: более поздняя дата; `combo`: локальный |
| `settings`, `language` | Подтягиваются из облака только при первом входе, если локальный сейв ещё не тронут (значения по умолчанию `freshSave()`) — в остальных случаях всегда побеждают локальные настройки устройства, так как тема/голос и т.п. — это настройки устройства, а не аккаунта |

Все счётчики мержатся через `max`, а не через сумму — это делает повторное слияние (например,
синк ещё раз до того, как другое устройство продвинулось дальше) идемпотентным, а не
задваивающим числа. Покрыто тестом `tests/cloud-sync-merge.test.ts`.
